# Кандидатогенерация для поиска услуг Авито

Первый этап поиска по услугам: по запросу пользователя найти в корпусе до 50 объявлений, среди которых окажутся те, что пользователь в итоге выбрал. Дальше эти кандидаты уходят на ранжирование, поэтому здесь важна полнота. Метрика — Recall@50: доля выбранных объявлений, попавших в 50 кандидатов, усреднённая по запросам.

## Результат

| Данные | Recall@50 |
|---|---|
| Валидация: 5 000 отложенных запросов из train | 0.939 |
| Закрытый бенчмарк платформы | 0.896 |

`answer.csv` в репозитории — файл, отправленный на платформу. `python main.py` воспроизводит его побайтно.

## Структура проекта

```
main.py                   весь пайплайн: данные → обучение → валидация → answer.csv
requirements.txt          зависимости с точными версиями

notebooks/analysis.ipynb  анализ данных, на котором построено решение
src/data.py               загрузка данных, запросы из train, разбиение для валидации
src/text.py               лемматизация и текстовые поля объявлений
src/retrieval.py          BM25, доля слов запроса в полях, символьные n-граммы
src/embeddings.py         дообучение e5-small и кодирование текстов
src/stats.py              статистика локаций, классификатор подкатегорий, история текста запроса
src/candidates.py         пул кандидатов из нескольких источников
src/features.py           признаки пар «запрос — кандидат»
src/ranker.py             модель отбора и метрика
src/pipeline.py           корпус с индексами и признаки для набора запросов
src/submission.py         запись answer.csv и проверка формата
```

## Как запустить

Нужны Python 3.12, около 7 ГБ оперативной памяти и 2 ГБ на диске под кэш. Интернет нужен один раз: при первом запуске с Hugging Face скачиваются веса `intfloat/multilingual-e5-small`, это около 470 МБ. Внешних API решение не вызывает.

```bash
python3.12 -m venv .venv
source .venv/bin/activate        # на Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Файлы задания `train.parquet`, `benchmark_queries.parquet` и `benchmark_items.parquet` нужно положить в папку `data/` в корне проекта. Затем:

```bash
python main.py
```

Что делает скрипт:

1. Собирает запросы из train и откладывает часть из них: одни для обучения модели отбора, другие для оценки.
2. На остальных парах train считает статистики, обучает классификатор подкатегорий и дообучает энкодер на CPU. Дообучение занимает около 25 минут.
3. Собирает кандидатов и признаки для отложенных запросов, обучает модель отбора и печатает качество на валидации.
4. Тем же способом отбирает по 50 кандидатов для запросов бенчмарка, пишет `answer.csv` и проверяет его на все требования к формату.

Прогон с нуля на MacBook с M5 занимает около 40 минут. Леммы, дообученная модель и эмбеддинги корпусов сохраняются в `cache/`, повторный запуск берёт их оттуда и занимает около 6 минут. Чтобы пересчитать всё с нуля, удалите `cache/`. Вывод повторного запуска:

```
[  0.1 мин] данные: 422596 пар для статистик, 20000 запросов для модели отбора, 5000 для оценки
[  1.8 мин] статистики, классификатор подкатегорий и энкодер готовы
[  4.5 мин] модель отбора обучена: 12838682 пар, 37 признаков
[  5.2 мин] валидация: полнота пула 0.9735, Recall@50 0.9393
[  5.9 мин] answer.csv записан и проверен: 2452 запросов по 50 кандидатов
```

Ноутбук с анализом открывается так:

```bash
jupyter lab notebooks/analysis.ipynb
```

Выводы ячеек в нём сохранены, так что читать его можно без запуска. Для перезапуска нужны те же файлы в `data/`, выполнение занимает около минуты. В ноутбуке по порядку:

- как из пар train получаются запросы;
- чем бенчмарк отличается от train и почему валидация устроена именно так;
- насколько корпус пересекается с объявлениями train;
- как устроены локации;
- насколько выбранные объявления соблюдают фильтры поиска;
- особенности значений: цены-заглушки, пропуски, объявления не из услуг.

## Данные

| Файл | Строк | Что внутри |
|---|---|---|
| `train.parquet` | 497 673 | пары «запрос — выбранное объявление» с признаками запроса и объявления |
| `benchmark_queries.parquet` | 2 452 | запросы бенчмарка без разметки |
| `benchmark_items.parquet` | 189 212 | корпус, в котором ищутся кандидаты |

У запроса есть текст, локация поиска, флаг поиска с доставкой, фильтры в текстовом виде и категория поиска. У объявления — заголовок, описание, параметры в текстовом виде, категория и подкатегория, цена, рейтинг и число отзывов, локация и координаты, флаги скрытого телефона и запрета сообщений. Флаг доставки равен 1 только в 12 строках train и ни разу в бенчмарке, поэтому как признак он не используется.

**Запросы в train.** Идентификатора запроса в train нет. После удаления 30 619 полных дублей остаётся 467 054 пары. Запросом считается уникальный набор признаков поиска, а все объявления, выбранные при нём, — его релевантными ответами. Получается 354 463 запроса с 73 874 уникальными текстами и 344 825 объявлений. У 85% запросов одно выбранное объявление.

**Чем бенчмарк отличается от train:**

- все тексты запросов бенчмарка, кроме одного, уникальны, и только 37% из них встречаются в train;
- запросов без фильтров в бенчмарке 63%, а в train, если брать по одному запросу на текст, 47%;
- 9% поисков бенчмарка идут без категории, в train таких почти нет;
- в train встречалось только около 10% объявлений корпуса.

**На чём обучалось и проверялось решение.** Из train отложено 25 000 запросов, по одному на уникальный текст: 20 000 для обучения модели отбора и 5 000 для оценки. На остальных 422 596 парах считаются статистики, обучается классификатор подкатегорий и дообучается энкодер. Пары с объявлениями отложенных запросов оттуда тоже убраны, иначе модели видели бы ответы заранее. Кандидатов для отложенных запросов решение ищет в корпусе того же размера, что у бенчмарка: все их выбранные объявления плюс случайные объявления train. Все модели обучаются один раз и без изменений применяются к бенчмарку, так что оценка на валидации относится ровно к отправленной системе.

## Как устроено решение

Два шага.

1. **Пул кандидатов.** Около 640 объявлений на запрос из нескольких источников:
   - BM25 по заголовку, параметрам и описанию: 300 лучших в совместимых локациях и 150 в ядре локации;
   - BM25 только по заголовку, 100 лучших в совместимых локациях;
   - BM25 без учёта локации, 100 лучших: удалённые услуги и соседние регионы;
   - косинус эмбеддингов дообученной e5-small: 200 лучших в совместимых локациях, 100 в ядре и 50 по всему корпусу.

   Совместимые локации — те, куда в train вели поиски из локации запроса. Ядро — те из них, куда ведёт не меньше 5% выборов, для города это обычно он сам. Если поиск шёл в категории, кандидаты берутся только из неё: в train так почти всегда.

2. **Отбор 50.** Градиентный бустинг оценивает для каждого кандидата вероятность, что его выберут, и берутся 50 лучших. Порядок внутри 50 на метрику не влияет, поэтому хватает бинарной модели без ранжирующей функции потерь.

## Признаки и почему именно они

Текстовые поля объявления — заголовок, параметры и первые 3000 символов описания — лемматизируются pymorphy3. Описание сильно помогает: BM25 только по заголовку и параметрам находит в топ-50 долю 0.475 выбранных объявлений, а со всеми полями — 0.629.

Всего у пары «запрос — кандидат» 37 признаков:

- **текст:** BM25 и доля слов запроса с весом idf, найденных в каждом поле; косинус по символьным n-граммам с заголовком, он ловит опечатки и слитное написание; косинус эмбеддингов; место кандидата среди кандидатов того же запроса. Короткий запрос совпадает с тысячами объявлений, и важна не только сила совпадения, но и то, насколько кандидат сильнее соседей;
- **локация:** доля выборов из локации запроса, которые пришлись на локацию объявления; совпадение локаций; расстояние от центра локации поиска. В 82% пар объявление из той же локации, что и поиск, но часть локаций поиска — регионы и вся страна, поэтому совместимость берётся из статистики;
- **подкатегория:** вероятность подкатегории объявления по тексту запроса и фильтрам; доля этой подкатегории среди выборов по точно такому же тексту в train. Подкатегория отделяет нужные услуги от просто похожих по словам;
- **фильтры поиска:** доля слов фильтра в параметрах объявления и соблюдение фильтра по рейтингу. Выбранные объявления соблюдают фильтры в 96–99% случаев;
- **объявление:** рейтинг, число отзывов, цена, скрыт ли телефон, запрещены ли сообщения, длина текстов;
- **запрос:** число слов, есть ли фильтры, встречался ли текст в train.

Признаков уровня конкретного объявления вроде «сколько раз его выбирали» нет: в train встречалось только около 10% объявлений корпуса, и на бенчмарке такие признаки почти всегда пустые.

## Модели и алгоритмы

- BM25 по леммам — своя реализация на разреженных матрицах; лемматизация — pymorphy3.
- TF-IDF по символьным 3–5-граммам заголовка.
- `intfloat/multilingual-e5-small`, дообученная контрастивно на 100 000 пар «запрос — выбранное объявление» из train: для запроса правильный ответ — его объявление, негативы — остальные объявления батча.
- Классификатор подкатегорий: логистическая регрессия (`SGDClassifier`) на TF-IDF слов и символьных n-грамм запроса и фильтров.
- Статистика «локация поиска → локация объявления» по train.
- Модель отбора: `HistGradientBoostingClassifier` из scikit-learn.

## Как проверялось качество до отправки

Качество мерялось на 5 000 отложенных запросах, устроенных как бенчмарк. В бенчмарке 37% текстов встречаются в train. Если брать из train по одной случайной группе на уникальный текст, доля знакомых текстов получается такой же, 38%, поэтому отложенные запросы выбираются именно так. Доля запросов без фильтров выровнена под бенчмарк: 63%.

Как менялось качество на валидации:

| Шаг | Полнота пула | Recall@50 |
|---|---|---|
| BM25 по всем полям в совместимых локациях, без модели отбора | — | 0.629 |
| модель отбора поверх пула BM25 | 0.865 | 0.849 |
| источник по ядру локации и эмбеддинги e5-small без дообучения | 0.963 | 0.926 |
| дообучение e5-small на парах из train | 0.974 | 0.939 |

Стандартная ошибка оценки на 5 000 запросах около 0.003. Поэтому изменения, которые двигали результат меньше чем на 0.002, в решение не вошли. Среди них настройки бустинга, дополнительные относительные признаки и дообучение энкодера на 200 000 парах вместо 100 000: оно дало +0.001, а учится вдвое дольше. Модель USER-base оказалась хуже e5-small и в 4–5 раз медленнее, rubert-tiny-turbo — заметно хуже.

Перед записью `answer.csv` проверяется по всем пунктам условия: шапка из двух колонок без индекса, все запросы бенчмарка без повторов, до 50 разных id в строке, формат id. Каждый `item_id` дополнительно сверяется с корпусом: неверный id проверка платформы пропускает молча, и метрика просто проседает.

## Результат на закрытых данных

На платформе Recall@50 = 0.896, на 4 пункта ниже валидации. Бенчмарк отличается от train сильнее, чем удалось повторить в валидации. Его корпус почти не пересекается с объявлениями train, а 9% запросов идут без категории: таких примеров в train почти нет, и модель отбора на них не училась. Долю знакомых текстов и запросов без фильтров в валидации удалось выровнять, а эти два отличия из train не повторить.

## Что нашлось при анализе и что с этим сделано

Данные:

- 30 619 строк train — полные дубли пар «запрос — объявление». Они удалены.
- У почти 10% объявлений цена -1, 0 или 1. Это заглушки вида «цена по запросу», они считаются пропуском.
- Часть локаций поиска — регионы или вся страна. Как локация объявления они не встречаются, а поиск из них ведёт в города внутри. На такие поиски приходится 11% пар train. Совместимость локаций берётся из статистики, а не из равенства id.
- Бенчмарк устроен иначе, чем train, это описано в разделе «Данные». Уникальность текстов и долю запросов без фильтров валидация повторяет. Для поиска без категории кандидаты берутся из всех категорий: около 1% корпуса — объявления не из услуг, и понадобиться они могут только таким поискам.

Промахи пула на валидации:

- Релевантное объявление есть в совместимых локациях, но его вытесняют объявления из соседних. 85% таких промахов — из самой локации поиска, и медианное место объявления внутри неё 55-е. Отдельный источник по ядру локации поднял полноту пула BM25 с 0.863 до 0.920.
- У запроса и объявления нет общих слов: опечатки вроде «педекюр», синонимы вроде «куплю лом металла» и «вывоз металлолома». Их находят эмбеддинги и символьные n-граммы.
- Объявление из локации, куда из локации запроса в train не ходили. Для них есть источники по всему корпусу.

Инженерные:

- Индексирование разреженных матриц в scipy на таких размерах идёт линейным проходом, поэтому значения пар ищутся своим бинарным поиском. Сборка пула ускорилась примерно в 30 раз.
- На MPS обратный проход недетерминирован, и веса энкодера от запуска к запуску расходятся. Поэтому энкодер дообучается на CPU, а на MPS только кодируются тексты: там результат повторяется.
- Первая версия признаков копировала строки с описаниями на каждую из 12 миллионов пар и не помещалась в память. Теперь всё, что зависит только от запроса или только от объявления, считается один раз и раздаётся по индексу.
- LightGBM на macOS требует системную библиотеку OpenMP, поэтому бустинг взят из scikit-learn.

## Воспроизводимость

Все сиды фиксированы, энкодер дообучается на CPU, косинусы округляются до четырёх знаков, а при равных скорах порядок определяет позиция в корпусе. Два прогона с нуля на одной машине дали побайтно одинаковый `answer.csv`, совпадающий с отправленным. На другом железе арифметика с плавающей точкой может немного отличаться, и тогда могут поменяться отдельные кандидаты на границе топ-50.

## Выводы

- Recall@50 на закрытых данных 0.896, на валидации 0.939: почти девять выбранных объявлений из десяти доходят до ранжирования. Порядок внутри 50 здесь не важен, его определит следующий этап.
- Больше всего дала модель отбора над пулом кандидатов: +22 пункта к чистому BM25. Ещё 8 пунктов дали источник по ядру локации и эмбеддинги, 1 пункт — дообучение энкодера.
- Разрыв в 4 пункта между валидацией и закрытыми данными, скорее всего, связан с отличиями бенчмарка от train, которые валидация не может повторить: поисками без категории и корпусом, который почти не пересекается с train.
- Что можно улучшить дальше: собрать обучающие примеры для поиска без категории и дообучать энкодер на тексте с началом описания. Без дообучения такой текст давал более полный пул, но кодируется почти втрое дольше.
